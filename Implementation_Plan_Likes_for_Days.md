# Implementation Plan: "Likes for Days" Caching, Resolution, and Filtering Fixes

## 1. Executive Summary & Goals

An audit of the end-to-end **"Get New ListenBrainz Data" $\rightarrow$ "Likes for Days" (Sync & Resolve)** workflow identified four caching/merging bugs that cause cache truncation, redundant MusicBrainz API queries, broken reverse cache lookups, and duplicate/unattributed rows, alongside two filtering enhancements needed to abridge the dataset before network enrichment:

1. **Bug #1 — Pre-Flight ListenBrainz Likes Truncation (`likes.json`):** The pre-flight sync in `gui_main.py` fetches only page 1 (`offset=0, count=500`) without pagination and atomically overwrites `likes.json`, wiping out ~4,260 cached likes previously fetched by `SyncManager`.
2. **Bug #2 — Redundant Pre-Flight Resolution & Unutilized Local History (`listens.jsonl.gz`):** Pre-flight resolution sends all unmapped Last.fm loves (954 tracks) to the MusicBrainz search API without checking if they already have a `recording_mbid` in `listens.jsonl.gz` (856 of 954 do) or filtering by minimum listen count / Top N.
3. **Bug #3 — Pipe-Vulnerable Cache Keys & Broken Reverse Lookup (`mbid_resolver_cache.json`):**
   * `parsing.make_track_key()` uses a single pipe `"|"` (`"artist|track|album"`), while `reporting.report_likes()` splits on `"||"`, making reverse lookups dead code.
   * Furthermore, single pipes `"|"` appear in **76 track names**, **60 album names**, and **9 artist names** in the local listening history (e.g., *The Ocean — "Miocene | Pliocene"* on *"Phanerozoic II: Mesozoic | Cenozoic"*), making `"|"` unsafe for key splitting.
   * When a Last.fm love matches an unnamed ListenBrainz like row by MBID, `report_likes()` discards the Last.fm `artist` and `track` strings.
4. **Bug #4 — Case-Sensitive Cross-Service Join, Divergent MBIDs, & Lost Albums:**
   * `report_likes()` matches Last.fm loves against ListenBrainz likes using case-sensitive `(artist, track_name)`. When Last.fm and ListenBrainz differ in both MBID and capitalization (e.g., *"Between the Buried and Me"* vs *"Between The Buried And Me"*), duplicate track rows are emitted with two different MBIDs—triggering duplicate duration lookups and double-counting listens/durations in Artist and Album aggregations.
   * `report_likes()` discards `album` from `mbid_resolver_cache.json`, and `get_resolved_likes()` only recovers `album` from `df` via exact `recording_mbid` match (missing 1,748 Last.fm loves whose MBID differs from `df["recording_mbid"]` but whose `(artist, track_name)` is present in `df` with a valid album).
5. **Filtering Changes (`min_listens` Default = 3 & Respecting `min_listens` + `topn` in "Likes for Days"):**
   * Change the default **Minimum Listen Count** in `gui_filters.py` from `5` to `3`.
   * Replace the hardcoded `>= 2` listen threshold in "Likes for Days" with the user's configured `min_listens` filter across pre-flight resolution, candidate duration fetching, and final aggregation.
   * Apply `topn` (and `min_listens`) prior to network enrichment so that only qualifying top candidates require MusicBrainz resolution and duration lookups.

## 2. Detailed Design & Proposed Changes

### 2.1 Redesigning the Resolver Cache Key & Value Schema (Addressing Bug #3)

#### Problem Analysis
In the current codebase:
* `parsing.make_track_key(artist, track, album)` returns `f"{a}|{t}|{alb}"`.
* Splitting a key string on `"|"` fails whenever an artist, track, or album title contains `"|"` (e.g., `"the ocean|miocene | pliocene|phanerozoic ii: mesozoic | cenozoic"` splits into 5 segments).
* Splitting on `"||"` also fails when the middle token is empty or when `"|"` sits adjacent to a delimiter.
* Even when splitting succeeds, keys are lowercased (`_clean_str`), so reconstructing display names from the key loses proper capitalization (`"the ocean"` instead of `"The Ocean"`).

#### Proposed Solution (Two-Part Hardening)

1. **Author Structured Metadata Inside the Cache Value (`enrichment.py` & `api_client.py`):**
   Update `mbid_resolver_cache.json` entries from `{"mbid": "...", "album": "..."}` to explicitly store the artist and track names alongside the MBID and album:
   ```json
   {
     "mbid": "fcfaa77a-220c-43cd-a360-3ef9ed117931",
     "artist": "The Ocean",
     "track": "Miocene | Pliocene",
     "album": "Phanerozoic II: Mesozoic | Cenozoic"
   }
   ```
   * **Why this matters:** Reverse lookups by `mbid` in `reporting.report_likes()` can read `cache_val["artist"]`, `cache_val["track"]`, and `cache_val["album"]` **directly from the JSON object fields** without splitting the cache key at all, while preserving original capitalization.

2. **Collision-Proof Composite Keys (`parsing.py`):**
   We have two strong options for the key string generated by `make_track_key(artist, track, album)` and `make_album_key(artist, album)`:
   * **Option A (Recommended): JSON-Serialized Array Key (`json.dumps([a, t, alb], ensure_ascii=False)`)**
     * Produces keys like `'["the ocean", "miocene | pliocene", "phanerozoic ii: mesozoic | cenozoic"]'`.
     * **Pros:** Mathematically injective/bijective for *any* arbitrary Unicode string (pipes, double-pipes, quotes, tabs, and empty strings are natively escaped by Python's C-accelerated `json.dumps` and parsed via `json.loads` in `parsing.parse_track_key()`). Still human-readable in `mbid_resolver_cache.json`.
   * **Option B: ASCII Unit Separator (`"\u001f"`) or Triple-Pipe (`"|||"`) with `parse_track_key()` Helper**
     * Uses a multi-character or control separator (stripping any separator occurrence from inputs in `_clean_str`).
   * **Backward-Compatible Cache Migration (`enrichment._load_resolver_cache`):**
     * Whichever key format is chosen, we can include a lightweight migration check when loading `mbid_resolver_cache.json` (or rebuild it cleanly, as you noted). Since 442 entries are currently in `mbid_resolver_cache.json`, an automatic migration helper can convert legacy `"a|t|alb"` keys (where `key.count("|") == 2`) into the new format and backfill `"artist"` and `"track"` fields into the value dict automatically, while discarding or re-resolving any ambiguous legacy keys containing extra pipes.

### 2.3 Fixing Cross-Service Merging, History Lookup, & Deduplication (Addressing Bugs #2, #3, #4)

#### Target File: `reporting.py` (`report_likes`, `get_resolved_likes`, `report_likes_for_days`)

1. **Build Fast Local History Index in `report_likes()` ([`reporting.py:810-982`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L810-L982)):**
   * Pre-index `df` (user listening history) once at the start of `report_likes()`:
     * `mbid_to_best_row`: maps `recording_mbid` $\rightarrow$ most complete `(track_name, artist, album, artist_mbid, release_mbid)` in `df` (vectorized/grouped instead of running `df[df["recording_mbid"] == mbid]` in a Python loop 4,727 times, which currently takes plusieurs seconds!).
     * `name_to_best_row`: maps `(artist.lower().strip(), track_name.lower().strip())` $\rightarrow$ most complete `(track_name, artist, album, recording_mbid, artist_mbid, release_mbid)` in `df`, preferring rows that have a non-empty `recording_mbid` and non-empty `album`.
2. **Step 1 (ListenBrainz Likes Base):**
   * Look up each `mbid` in `mbid_to_best_row` ($O(1)$ dict lookup instead of $O(N)$ DataFrame scan per MBID).
   * On miss, use a pre-built reverse lookup dict `mbid_to_cached_info` from `resolver_cache`:
     * Read `artist`, `track`, and `album` from `cache_val` (or `parsing.parse_track_key(cache_key)` for legacy entries).
     * Check `name_to_best_row` by `(artist.lower(), track.lower())` to enrich `album`, `artist_mbid`, and `release_mbid` from history if available.
3. **Step 2 (Joining Last.fm Loves):**
   * **Step 2a (Resolution Priority for Last.fm Loves):**
     For each `(artist, track, lfm_mbid)` in `lastfm_loves`:
     1. Check `name_to_best_row.get((artist.lower(), track.lower()))` in listening history `df` AND `lb_name_to_row_lower` (ListenBrainz likes):
        * **Crucial fix for divergent MBIDs:** If the track is already present in ListenBrainz likes (`lb_name_to_row_lower` by case-insensitive `(artist.lower(), track.lower())`), match it directly to that ListenBrainz row! This prevents Last.fm's divergent MBID or capitalization from spawning a duplicate row.
        * If the ListenBrainz like row had blank `artist`/`track_name` (and matched by `mbid` in Step 2b), backfill `artist`, `track_name`, and `album` from the Last.fm love / `name_to_best_row`.
     2. For Last.fm loves not already in ListenBrainz likes, resolve `recording_mbid` and `album` using the following local-first priority:
        * **(i) Listening History (`name_to_best_row`):** If the user has scrobbled `(artist, track)` in `df` with a valid `recording_mbid`, use `df`'s `recording_mbid` (and `album`, `artist_mbid`, `release_mbid`). Using `df`'s `recording_mbid` ensures 100% alignment with `df`'s listen counts and album metadata!
        * **(ii) Resolver Cache (`resolver_cache`):** Look up `make_track_key(artist, track, "")` (or a pre-built `(artist.lower(), track.lower())` index over `resolver_cache` so entries resolved with an album name also match!). Preserve `cached.get("album")`!
        * **(iii) Last.fm MBID (`love.get("mbid")`):** Use if non-empty, and still recover `album`, `artist_mbid`, and `release_mbid` from `name_to_best_row` in `df` if `(artist.lower(), track.lower())` exists in history!
4. **Recover Metadata by Both MBID and Case-Insensitive Name in `get_resolved_likes()` ([`reporting.py:1084-1102`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L1084-L1102)):**
   * If `album`, `artist_mbid`, or `release_mbid` is still empty on a row in `resolved_likes_df`, fall back from `mbid_lookup` to `name_to_best_row[(artist.lower(), track_name.lower())]`.
   * **Impact on your dataset:** Reduces resolved likes with missing albums from **1,789** down to **< 40**!
5. **Deduplicate Canonical Tracks in `report_likes_for_days()` ([`reporting.py:1232-1258`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L1232-L1258)):**
   * After MBID and case-insensitive name normalization, ensure `full_track_df` is deduplicated on `(artist.str.lower(), track_name.str.lower())` (keeping the entry with the highest listen count / valid album) before aggregating `full_artist_df` and `full_album_df`. This guarantees no track is ever double-counted in Artist or Album totals.

#### 2. Respect `min_listens` and `topn` Across All 3 Stages of "Likes for Days"

Let `effective_min_listens = max(1, min_listens)` (defaulting to `3` from the UI, or at least `1` if the user enters `0` so tracks with 0 listens in the selected time window are excluded).

* **Stage 1 — Pre-Flight Unmapped Likes Resolution ([`gui_main.py:656-679`](file:///home/jasper/Projects/BrainzMRI/gui_main.py#L656-L679)):**
  When `sync_and_resolve` is chosen:
  1. Apply the active time-range filter (`time_start_days`, `time_end_days`) to `base_df` so pre-flight uses the exact same listening window as `ReportEngine.generate_report()`.
  2. Compute `name_counts` (listens per `(artist.lower(), track_name.lower())`) and `hist_has_mbid` (set of `(artist.lower(), track_name.lower())` that already have a valid `recording_mbid` in `df`).
  3. Filter `lastfm_loves` needing resolution to tracks where:
     * Last.fm `mbid` is empty, **AND**
     * `(artist.lower(), track.lower())` is **not** already in `hist_has_mbid` (since `df` already has its `recording_mbid`), **AND**
     * `name_counts.get((artist.lower(), track.lower()), 0) >= effective_min_listens`.
  4. **Impact on your dataset (at `min_listens = 3`):**
     Instead of passing **954** tracks to `resolve_missing_mbids()`, only **32** tracks in your entire history have $\ge 3$ listens and lack an MBID in `listens.jsonl.gz` and `lastfm_loves.json`!
  5. **Optional `topn` Abridgement in Pre-Flight:** Sort those remaining unmapped tracks by listen count descending and cap at `topn` (if `topn > 0`).

* **Stage 2 — Candidate Track Selection Prior to `fetch_recording_durations()` ([`report_engine.py:213-265`](file:///home/jasper/Projects/BrainzMRI/report_engine.py#L213-L265)):**
  1. Replace the hardcoded `if max(c_mbid, c_name) >= 2:` check at [`report_engine.py:235`](file:///home/jasper/Projects/BrainzMRI/report_engine.py#L235) with:
     ```python
     effective_min_listens = max(1, min_listens)
     listens_cnt = max(c_mbid, c_name)
     if listens_cnt >= effective_min_listens:
     ```
  2. Deduplicate `candidate_tracks` by **both** `mbid` and `(artist.lower(), track_name.lower())` so two different MBIDs for the same song never both get queried.
  3. **Respecting `topn` Before Duration Enrichment:**
     Sort `candidate_tracks` by `listens_cnt` descending and, when `topn and topn > 0`, truncate `candidate_tracks = candidate_tracks[:topn]` **before** calling `enrichment.fetch_recording_durations()`.
     * *Why this speeds up reporting & debugging:* At `min_listens = 3`, there are 2,095 qualifying liked tracks in your history (which would require ~38 minutes of MusicBrainz API calls on a cold `duration_cache.json`). Truncating `candidate_tracks` to `topn` (e.g., `100`, or `20` when debugging) ensures `fetch_recording_durations()` queries **at most `topn` tracks**, reducing cold-cache enrichment time from ~38 minutes to ~1 minute (and < 1 second on warm cache).
     * *(See Section 4 below for a design question on whether `topn` pre-truncation should use `topn` directly or only apply to `track_df` / use `df["duration_ms"]` for non-Top-N tracks).*

* **Stage 3 — Final Aggregation (`reporting.report_likes_for_days` in [`reporting.py:1105-1335`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L1105-L1335)):**
  1. Accept `min_listens: int = 3` in `report_likes_for_days()` and replace `if listens < 2: continue` ([`reporting.py:1182`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L1182)) with `if listens < max(1, min_listens): continue`.
  2. Keep the final `.head(topn)` truncation on `top_track_df`, `top_artist_df`, and `top_album_df` ([`reporting.py:1317-1320`](file:///home/jasper/Projects/BrainzMRI/reporting.py#L1317-L1320)).
  3. Update UI prompt text in [`LikesSyncPromptDialog`](file:///home/jasper/Projects/BrainzMRI/gui_actions.py#L185-L188) and progress bar strings in [`report_engine.py`](file:///home/jasper/Projects/BrainzMRI/report_engine.py#L214-L253) to display `{effective_min_listens}+ listens` dynamically instead of hardcoded `2+ listens`.

## 4. Finalized Design Decisions (Implemented)

1. **Resolver Cache Key Format & One-Time Migration:**
   * Adopted **JSON-serialized array keys** (`json.dumps([a, t, alb], ensure_ascii=False)`) in `parsing.make_track_key()`, `parsing.make_album_key()`, and `parsing.make_track_key_series()`, paired with `parsing.parse_track_key()` and explicit `"artist"`, `"track"`, and `"album"` fields inside `mbid_resolver_cache.json` value objects.
   * Executed a one-time migration of all 954 existing entries in `cache/global/mbid_resolver_cache.json` to the new JSON-array key format and structured value schema.

2. **Filtering Behavior (`min_listens` Only for Search Abridgement; Default = 3):**
   * Updated the default **Minimum Listen Count** in `gui_filters.py` from `5` to `3`.
   * Skipped pre-enrichment `topn` capping to avoid distorting artist/album duration totals; instead, **only `min_listens`** is used to abridge pre-flight resolution and candidate duration enrichment.
   * Propagated the active `min_listens` count into `LikesSyncPromptDialog`, progress bar messages, status bar output, and treemap chart titles so the user always sees what listen threshold is included.
